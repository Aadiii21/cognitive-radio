# BPSK Receive Path — Stage 1 Report (2026-11-23)

> **Status (25 Nov 2026):** this document is a historical record of stage 1 of the BPSK receive path (23 Nov); it is kept unchanged below. Final state: the over-the-air Pluto → RTL-SDR link was tested on 23 Nov (BPSK/QPSK/16-QAM BER matches theory), a DL modulation classifier was added (98.5 % on real OTA captures), and the hardware closed loop was removed from scope. Current documents: `MASTER_README.md`, `docs/RESULTS_AND_DISCUSSION.md`, `docs/LIMITATIONS.md` and the reports in `docs/reports/`.

**Hardware status: not run.** All of this was done without GNU Radio or SDR
hardware. All BER figures below come from simulated channels. They show the
logic is consistent with itself, not that the RF path works.

Audit this stage is based on: `docs/HARDWARE_PATH_AUDIT.md`.

## Tests executed (actual results)

* Full suite, no GNU Radio: **179 passed, 3 failed**. The 3 failures were already there: `gnuradio.iio` is not installed.
* Full suite with a stub `gnuradio` package on `PYTHONPATH`: **182 passed**. This shows the adapter changes are compatible with the existing mocked tests.
* Software channel cases the receiver passes: TX 2 083 333 / RX 2 048 000 S/s; CFO up to ±37 kHz; arbitrary phase including π; fractional delay; DC offset; 8-bit quantisation; Es/N0 11–20 dB → BER 0. Noise-only input → no detection, no BER.
* Low SNR: at Es/N0 = 4 dB over more than 15 000 payload bits, the measured BER is close to the theoretical 1.25 × 10⁻² and within the test's tolerance (≤ 1 dB implementation loss). The SNR estimate is within ±1.5 dB at 8 and 14 dB.
* A first version of the phase tracker diverged at 4 dB (BER 0.116), caught by this test. The fix: accept a decision-directed correction only if it improves the decision metric.

## Hardware bring-up (on the Arch machine)

1. `python scripts/run_hardware_experiment.py --freq 866000000` (dry run). This checks the waveform and prints the occupied band. 865.000 MHz puts about half the signal below 865 MHz.
2. Resolve audit item B1 (`ch_en`) against the installed gr-iio before the first transmission.
3. Use a conducted path with attenuation sized from a **measured** Pluto output. Start with more attenuation than you think you need.
4. `python scripts/run_hardware_experiment.py --enable-rf --freq 866000000`. You will be asked to type `TRANSMIT`.
5. Check the result file in this order:
   - clipping fraction, which should be about 0;
   - the RX rate `rtl_sdr` reported;
   - frames detected and the detection metric;
   - preamble bit errors;
   - only then payload BER.
6. TX rate readback is now automatic (Stage 1.1, below). The runner reads
   `ad9361-phy` output `voltage0/sampling_frequency`, `voltage0/hardwaregain`,
   `voltage0/rf_bandwidth` and `altvoltage1/frequency` (TX_LO) while
   transmitting, and the receiver uses the read-back rate.

## Remaining limitations

* No physical RF result exists. Completion checklist items 4–9 of handoff §15 are still open.
* B1 (`ch_en`), B2 (`top_block.wait(timeout)`), B4 (Pluto rate) and B6 (`rtl_sdr` exit code after SIGINT) can only be resolved on the real machine.
* Timing is per-burst, from the preamble (no symbol-timing loop). That is enough for 576-symbol bursts at ppm-level clock offsets. It would not be enough for long continuous frames.
* The CFO search range is ±100 kHz (`max_cfo_hz`), about ±115 ppm at 866 MHz.
* `RTLSDRReceiver.detect_signal()` (A13) still produces a heuristic "SNR/BER/PDR". It is used by `pipelines/integrated_pipeline.py` and the demo scripts and is unchanged in this stage. Do not cite its numbers as measurements.
* QPSK and 16-QAM are not addressed yet (handoff Step 5).
* `combined_payload.json` (B3) looks like sums of bits rather than packed bytes. The v2 frame uses a uniform random payload instead. Pass `--payload-hex` to `bpsk_frame` to reuse a specific payload.
